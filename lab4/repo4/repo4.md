## 一、实验内容

### 1. 实验目标与开发环境

本实验使用微信小程序原生框架开发一个推箱子小游戏。在完成地图绘制、角色移动、箱子推动和通关判断等基本要求的基础上，参考 `doc4` 中的项目改进建议，对关卡数量、游戏状态、操作反馈和代码结构进行了进一步完善。

项目最终以“冰原推箱子”为主题，共设计 12 个 8×8 关卡，并实现关卡分组、练习与挑战模式、顺序解锁、最佳步数、星级评价、撤销、死锁提醒、异步方向提示、棋盘手势、触觉反馈和本地数据迁移等功能。主要练习内容包括：

- 使用 Canvas 绘制二维游戏地图和角色素材；
- 将地图数据、游戏规则、提示算法和本地存储拆分为公共模块；
- 处理墙体碰撞、箱子推动、撤销和胜利判断；
- 使用触摸事件实现移动端滑动控制；
- 使用异步搜索实现方向提示，并处理取消和超时降级；
- 使用本地缓存保存成绩与设置；
- 通过自动化测试验证游戏引擎、关卡和页面规则。

### 2. 项目结构与页面功能

小程序注册首页和游戏页两个页面。首页负责展示关卡和游戏进度，游戏页负责绘制棋盘、接收操作并更新游戏状态。

### 5. 游戏引擎拆分与地图校验

为避免把所有规则写在页面中，项目新增 `utils/game-engine.js`。该模块不依赖页面组件，主要提供以下接口：

```javascript
module.exports = {
  BOARD_SIZE,
  HISTORY_LIMIT,
  createGame,
  move,
  simulateMove,
  undo,
  isWin,
  isDeadlocked,
  findDeadlockedBox,
  validateLevel
}
```

`validateLevel()` 会在游戏开始前检查：

- 地图必须是 8×8 二维数组；
- 格子值必须在 0—5 范围内；
- 玩家必须且只能有一个；
- 箱子数量必须与目标数量相同；
- 关卡至少包含一个箱子和目标。

`createGame()` 将静态地图拆分为地形、箱子位置、玩家位置、移动步数和历史记录。这样箱子或玩家经过目标点后，目标地形仍然能够被保留。

### 7. 移动、推箱和胜利判断

方向键和滑动手势最终都会调用统一的 `move(direction)`。引擎先计算玩家下一格：如果是墙体或地图外区域则拒绝移动；如果下一格存在箱子，则继续检查箱子后方是否可通行、是否有另一个箱子；只有条件满足时才同时移动箱子和玩家。

成功移动后，步数加一并保存操作前快照；无效操作不增加步数，也不写入历史。箱子推动完成后调用 `isWin()`，只有全部箱子都位于目标点时才算通关。

游戏页会根据结果显示不同文字反馈，例如“推动成功，继续规划路线”“箱子后方被挡住”或“这个方向无法移动”，无效方向键还会短暂显示错误状态。

### 8. 方向键布局与棋盘手势

方向控制区使用两行布局：第一行只放上方向，第二行依次放左、下、右方向。四个按钮分别占据独立位置，避免按钮重叠，并使控制区域整体居中。

为了适应手机操作，Canvas 还支持上、下、左、右滑动。开始触摸时记录坐标，结束时比较横向和纵向位移；位移达到 28px 才触发移动，并使用 `touchHandled` 保证一次滑动最多移动一步。

```wxml
<canvas
  canvas-id="gameCanvas"
  disable-scroll="true"
  catchtouchstart="onTouchStart"
  catchtouchmove="onTouchMove"
  catchtouchend="onTouchEnd"
  catchtouchcancel="onTouchCancel">
</canvas>
```

`disable-scroll` 和 `catchtouchmove` 会在棋盘区域截获触摸移动，因此用户在棋盘上纵向滑动时不会带动整个页面；棋盘以外仍然可以正常滚动。

> **截图位置 5：居中的方向键、操作按钮以及棋盘滑动真机效果。**

### 9. 撤销、重新开始与死锁提醒

每次有效移动前，引擎保存玩家位置、箱子矩阵和步数，最多保留最近 50 步。执行撤销时读取最后一份快照并恢复状态，无历史时不会发生任何变化。

撤销次数根据模式采用不同规则：

- 练习模式不限次数，按钮显示“撤销一步（不限）”；
- 挑战模式每次关卡尝试最多成功撤销 3 次；
- 只有撤销真正成功后才扣减次数；
- 重新开始或重新进入关卡后恢复次数；
- 撤销操作不会恢复已经消耗的提示次数。

死锁检测会检查不在目标点上的箱子。如果箱子的竖直方向和水平方向都被墙体阻挡，则提示“箱子进入非目标死角，请撤销或重新开始”。该提示不会强制结束游戏，用户仍可选择撤销或重开。

> **截图位置 6：练习模式不限撤销、挑战模式剩余次数和死锁提醒。**

### 10. 异步智能方向提示

`utils/hint-engine.js` 使用紧凑的玩家位置和箱子位置编码进行异步 BFS 搜索。搜索到通关路径后返回最短已找到路径的第一步，不会直接修改当前棋盘、移动步数或撤销历史。

默认搜索参数如下：

```javascript
const DEFAULT_OPTIONS = {
  batchSize: 250,
  maxStates: 50000,
  timeoutMs: 1200,
  isCancelled: () => false
}
```

每批最多处理 250 个状态，再通过异步任务将控制权交还界面，避免长时间阻塞。搜索超过 50,000 个状态或 1,200ms 后，算法自动降级为安全启发式：枚举可以推动的箱子，排除已知墙角死锁，并综合箱子到目标的一对一最小距离、目标占用数量和移动代价选择方向。

每次关卡尝试最多成功使用 3 次提示。计算期间按钮显示“正在计算…”并禁止重复点击；成功显示“建议向上/下/左/右”，对应方向键短暂高亮后扣减一次。未找到安全方向、计算失败或请求被取消时不扣次数。

玩家移动、撤销、重新开始或退出页面时会更新请求编号，使旧搜索结果失效，避免过期结果覆盖新局面。

> **截图位置 7：提示计算中状态、文字方向建议和方向键高亮效果。**

### 11. 练习与挑战模式、解锁和星级

首页提供练习模式开关。练习模式默认开放全部关卡，适合自由体验；挑战模式下只有第一关初始开放，完成上一关后才能进入下一关。即使用户通过页面地址直接打开未解锁关卡，游戏页也会再次校验并返回关卡列表。

星级根据实际步数和推荐步数计算：

```javascript
function getStars(moves, parMoves) {
  if (!moves) return 0
  if (moves <= parMoves) return 3
  if (moves <= Math.ceil(parMoves * 1.2)) return 2
  return 1
}
```

首页显示已完成关卡数、累计星星数、每关最佳步数和评级。通关弹窗显示本次步数、推荐步数、最佳记录和获得星级，并提供下一关、再玩一次或返回关卡列表的操作。

## 二、问题总结与体会

### 1. 实验中遇到的问题及解决方法

（1）**棋盘滑动会带动整个页面。** 最初只监听触摸开始和结束，用户在棋盘上纵向操作时，页面滚动也会同时发生。解决方法是在 Canvas 上设置 `disable-scroll="true"`，使用 `catchtouchmove` 截获棋盘手势，同时保留 28px 阈值和单次触发标记。这样棋盘内滑动只控制角色，棋盘外仍可正常滚动。

（2）**移动按钮重叠，操作区没有居中。** 方向键和撤销、提示、重新开始、关卡列表按钮曾因定位与宽度设置发生重叠。解决方法是将方向键拆分为上下两行的 Flex 布局，将功能按钮拆为两个等宽操作行，并由父容器统一控制间距和居中。

（3）**撤销和提示没有规则限制。** 如果挑战模式可以无限撤销或连续请求提示，关卡挑战性会明显降低。解决方法是练习模式撤销不限次数，挑战模式每次尝试最多成功撤销 3 次；两种模式下的方向提示均限制为 3 次，并且只在操作真正成功时扣减。

（4）**方向提示容易阻塞界面或给出过期结果。** 同步搜索复杂局面会影响按钮响应，而玩家在搜索期间移动后，旧结果也可能不再适用。解决方法是将 BFS 拆成每批 250 个状态的异步任务，设置状态数和时间上限，并在超限时降级为安全启发式。移动、撤销、重开和退出页面都会取消旧请求。

（5）**简单的距离提示可能把箱子推入死角。** 只选择离目标最近的方向，没有考虑箱子一旦进入非目标墙角就无法拉回。解决方法是在游戏引擎和提示引擎中加入墙角死锁判断；启发式枚举推动方案时先排除已知死锁，再比较箱子与目标的最小匹配距离。

（6）**页面规则和引擎逻辑混在一起不便测试。** 如果移动、撤销和提示全部直接修改页面数据，测试必须依赖完整微信环境。解决方法是拆分 `game-engine.js`、`hint-engine.js`、`data.js` 和 `storage.js`，其中 `simulateMove()` 可以在不记录历史的情况下模拟移动，提示搜索不会污染真实游戏状态。

（7）**新增关卡可能出现不可解或数据格式错误。** 单靠人工试玩难以稳定覆盖 12 关。解决方法是增加地图校验与关卡可解性测试，自动检查地图尺寸、格子值、玩家数量、箱子与目标数量，并通过求解器验证全部关卡能够完成。

（8）**手机预览包超过 2MB。** 设计参考图和测试目录被开发者工具计入上传源码，导致错误码 `80051`。解决方法是在项目配置中排除 `design` 和 `tests`，开启忽略未使用文件，只上传运行所需页面、脚本和素材。

（9）**本机截图路径不能用于 CSDN。** 本机绝对路径只在当前电脑有效，上传博客后其他用户无法访问。因此本报告统一保留截图位置；发布到 CSDN 时再上传图片，并将占位文字替换为平台生成的网络图片地址。

### 2. 实验收获与体会

通过本次实验，我完成了一个包含 12 个关卡、两种游戏模式和完整操作反馈的微信推箱子小程序，对 Canvas 游戏从数据表示、画面绘制、输入处理到状态持久化的开发流程有了更系统的认识。

在游戏规则方面，我认识到推箱子并不只是交换角色和箱子坐标。地形、动态对象和目标状态需要分层保存，移动前还要依次判断边界、墙体、箱子和箱子后的格子。将这些规则封装为纯函数后，页面代码更加清晰，自动化测试也更容易编写。

在移动端交互方面，按钮可点击并不代表真机体验已经完整。棋盘手势与页面滚动冲突、按钮重叠、触摸位移过小和一次滑动重复触发，都会直接影响游戏可玩性。通过 Canvas 截获手势、设置滑动阈值、统一 Flex 布局和提供文字状态反馈，操作体验得到明显改善。

在算法方面，BFS 可以给出通关路径的第一步，但搜索规模不能无限增长。通过分批异步处理、时间与状态上限、安全启发式降级以及请求取消机制，我进一步理解了算法正确性、响应速度和界面状态一致性之间的平衡。

在产品规则方面，练习模式和挑战模式面向不同需求。练习模式开放关卡并允许无限撤销，降低学习成本；挑战模式采用顺序解锁和撤销限制，保留挑战性。最佳步数与星级评价则为通关之后提供了继续优化路线的目标。

在工程质量方面，地图校验、12 关可解性测试、存储迁移和上传包排除规则说明，小程序不仅要在模拟器中“能够运行”，还需要考虑数据错误、版本升级、异步竞态、真机手势和平台上传限制。通过这些改进，项目的稳定性、可维护性和完整度都得到提升。
